# 归类决定写到哪里：目的地

> 创建：2026-09-26（同日由「规则集的来源：订阅与支配」改写，原稿见本文件的 git 历史）
> 状态：v1.2.0 实现（2026-09-26）。用法见 README 第四节「目的地」；服务端的一个实现是作者自己的规则仓库（私有，不公开）。
> 边界：clash-review 把归类决定写到哪里，以及写到规则服务时用的写入协议。不在这里：订阅、浏览、覆盖别人的规则集（Clash Verge 与内核的事）；编辑已有规则（规则所在的服务自己提供管理界面）。
> 失效判据：mihomo 不再支持 `PUT /providers/rules/<名字>`，或 clash-review 不再以 Clash 的规则集为写入对象时，本篇整体失效。

---

## 一、clash-review 做什么，不做什么

| 做 | 不做（已经有人做） |
|---|---|
| 从内核日志找出被 `MATCH,REJECT` 拦下的连接，附上证据与推荐，由人归类 | 按网址取规则集、定时更新、失败时用缓存：内核本身（`type: http`） |
| 把归类决定写到**目的地**，并让内核取到 | 列出规则集、看条目数、手动更新：Clash Verge 的规则集页面、内核接口 `/providers/rules` |
| 在自己写入的范围内做写入前的检查（冗余、重叠） | 在订阅来的规则前面插自己的规则来覆盖：Clash Verge 的扩展配置（Merge）或 profile 的规则段 |
| | 检索、改类、删除已有规则：规则在哪里，就由那里提供管理界面。本机文件就直接改文件；规则服务就用它的管理页 |

原稿曾打算在 clash-review 里加「订阅模式」：自己按网址取别人的规则集、列在规则页里、通过收件箱覆盖。这样做等于把一个 Clash 客户端重新实现一遍，已否定（见第四节）。

## 二、两种目的地

每类（域名 / IP × 拉黑 / 直连 / 代理）写到哪里，由目的地决定。一台电脑只用一种目的地。

### 本机文件（默认，就是现在的做法）

- 写到 Clash 配置里每类第一个 `type: file` 规则集（README 第四节的「收件箱」）。
- 写入前的检查看 Clash 配置里的全部 `domain` / `ipcidr` 规则集，`http` 的读 `path` 处的本地缓存（v1.1.0 起）。这是能读就读，缓存旧了判断也会跟着旧，`status` 报出条数不一致。clash-review 不自己去取线上文件。
- 改动要在 Clash Verge 里重新激活才进内核（服务模式下内核读的是副本）。
- 规则页只显示这几个文件，可以检索、改类、删除，因为它们就是这台电脑自己的规则。

### 规则服务（写入接口）

用户自己维护一个在线规则服务，多台设备按网址订阅它。clash-review 持有它的写入密钥，把决定直接写进线上正本。

- `settings.json` 的 `destination`：写入接口地址 `endpoint`、密钥文件 `key_file`、每类写进哪个规则集 `rulesets`（`{"domain": {"reject": "<id>", …}, "ip": {…}}`）。配了它，就不再写本机文件，也不要求 Clash 配置里有收件箱。
- 写入前的检查交给服务端：服务端掌握全部规则，冲突、重复由它校验（`422`），提示放在返回结果里，clash-review 原样显示。clash-review 不去读这个服务的规则文件。
- 写入成功、服务端报告已上线后，clash-review 在 Clash 配置里找到网址对应的 `type: http` 规则集，调用 `PUT /providers/rules/<名字>` 让内核立即重新取，再用 `ruleCount` 核对。找不到对应的就跳过：内核按自己的间隔会取到。
- **在上线之前决定不会丢**：写入失败（连不上、`409`、`422`）时，这一项留在待审里，报出原因。已提交但还没上线的主机记下来，这段时间里又被拦下的连接不再放回待审，上线后清掉这份记录。
- 连不上服务端时明确报错，不自动改写到本机文件。自动回落就需要一个程序事后把本机的条目搬上线再清掉，又回到了第四节否定的做法。
- 写入密钥只在 clash-review 的后端（Python 进程）里用，不进 Clash 配置，不进网址，不发给浏览器。网页发起的写操作沿用现有防护（自定义请求头、校验 Origin）。
- 规则页在这种目的地下不列条目，只给出服务端管理页的链接（如果服务端提供）。

## 三、写入协议（草案 v1）

读取不需要新协议：各设备按 Clash 的 `type: http` 规则集网址取。下面只约定写入。clash-review 用到的是「列出、提交、查上线」；规则服务自己的管理页也可以用同一套接口。

### 凭据

- 请求带 `Authorization: Bearer <写入密钥>`。写入密钥与设备读取用的密钥（如果服务端有）必须是两把。
- 密钥放在 `key_file` 指向的文件里，一行，不写进 `settings.json`。

### 接口

| 请求 | 作用 | 返回 |
|---|---|---|
| `GET {endpoint}/rulesets` | 列出凭据能写的规则集。加 `?entries=1` 同时返回条目 | `[{"id", "behavior": "domain" \| "ipcidr", "path", "version", "count"[, "entries"]}]`。`path` 是读取网址的结尾部分，clash-review 用「网址以它结尾」找到 Clash 里对应的规则集，这样网址里带的设备密钥不必写进设置 |
| `GET {endpoint}/rulesets/{id}` | 读一个规则集 | `{"version", "entries": [...]}` |
| `POST {endpoint}/changes` | 提交一批改动，**整批原子**：要么全部生效，要么都不生效 | 见下 |
| `GET {endpoint}/deployments/{ref}` | 查一次提交是否已上线 | `{"state": "pending" \| "live" \| "failed"}` |

`POST /changes` 的请求体：

```json
{
  "base": {"<id>": "<读到的 version>"},
  "ops": [
    {"op": "remove", "ruleset": "<id>", "entry": "+.example.com"},
    {"op": "add",    "ruleset": "<id>", "entry": "+.example.com"}
  ]
}
```

- **改类**就是同一批里的一条 `remove` 加一条 `add`。它必须原子：中途失败只剩一半，这个条目就会凭空消失或同时留在两类里。
- `base` 可选。给了就逐个比较，有一个对不上（期间别处改过）就返回 `409`，附上当前的 `version`，不做任何改动。clash-review 新增条目时不带 `base`（只加不改，不怕别处的改动）；改类、删除要带。
- 服务端校验条目：域名写法、`+.` 前缀、CIDR 合法；单个 IP 必须写成 `/32` 或 `/128`（mihomo 会跳过裸 IP，见 README 第六节）；改动后不能出现同一条目同时在两类。不合法 → `422`，逐条写明原因。
- `add` 的条目已存在、`remove` 的条目不存在：不算错，结果里标为「无变化」。被已有的更大范围条目覆盖、与别的类重叠：照常写入，在 `notes` 里说明。
- 成功时：
  - `200`：新内容**已经**能从读取网址取到。返回 `{"versions": {…}, "results": [...], "notes": [...]}`；
  - `202`：服务端还要构建、部署。返回同样的正文，外加 `Location` 指向 `/deployments/{ref}`。clash-review 轮询它直到 `live`，再让内核重新取。超过上限就报「已提交但尚未上线」，不重复提交。
- 凭据不对 → `401`；凭据对但无权写这个规则集 → `403`。

### 不在协议里的

- 一个规则集属于拉黑、直连还是代理：这由各设备的 Clash 配置里 `RULE-SET` 那一行决定，不是规则集本身的属性。
- 服务端怎样存、怎样构建、分几层、给哪些设备生成什么格式，管理页长什么样。

## 四、否定结论

- **收件箱加搬运**（作者本机 2026-09-25 的做法）：clash-review 只写本机收件箱，另一个程序把新条目并入规则仓库、推送、部署，等 Clash 取回线上后再清空收件箱。问题：规则页里只有一个随时被清空的中转站，看不到也改不了真正的规则；一条规则要多次复制、跑很多步才生效，任何一步失败都会卡住；要改已有规则，还得另造一条「删除请求」通道。根源是编辑的一方没有写线上正本的权限，只能间接写。
- **本机文件为正本、线上只做单向发布**：规则就不再是「线上的、谁都能订阅的」，clash-review 也得懂某个特定服务端的分层结构。多台设备本来就需要线上那份。
- **在 clash-review 里做「订阅模式」**（本篇原稿）：自己按网址取别人的规则集、列在规则页、通过收件箱覆盖。取、缓存、更新是内核的事，列出与更新是 Clash Verge 的事，覆盖有 Clash Verge 的扩展配置，做下去就成了一个 Clash 客户端的外壳。clash-review 只保留别人不做的那一段：审查与归类。

## 五、实现时定下的

- 已提交的决定每 15 秒查一次（watch 与网页的后台线程），半小时仍未上线就不再等，`status` 报出来；记录保留一天。
- 「刚提交、还没上线」的条目不另记名单：提交后立即重取服务端条目，它们马上算作已有规则，watch 就不会把它们放回待审。
- 本机 profile 里的收件箱规则集可以留着：规则服务目的地下本工具不再写它、也不要求它存在，用户可以手工放临时规则。
- `GET /deployments/{ref}` 一律返回 `200`，状态在 `state` 里。
