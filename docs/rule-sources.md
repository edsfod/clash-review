# 规则集的来源：订阅与支配

> 创建：2026-09-26
> 状态：设计稿，未实现。实现后本篇的「待定」清空，README 第四节改写为指向这里。
> 边界：clash-review 怎样对待 Clash 配置里不是它自己的规则集，以及改线上规则集用的写入协议。规则集服务端怎样实现这份协议不在这里，由各服务端自己写。
> 失效判据：mihomo 不再支持 `type: http` 规则集或 `PUT /providers/rules/<名字>`，或 clash-review 不再以 Clash 的规则集为写入对象时，本篇整体失效。

---

## 一、为什么要分两种

clash-review 与规则集是两样独立的东西：

- clash-review 可以用任何人发布的规则集；
- 一份规则集可以被任何设备、任何客户端（Clash、Shadowrocket、v2rayNG……）订阅，也可以被别的类似 clash-review 的工具使用。

所以规则集在线上，两者只通过线上的网址相连。多台设备要用同一套规则，线上那份也是必需的。

用户通常改不了别人服务端上的规则集，只能在本地加一层自己的规则、排在前面，把它覆盖掉。但如果规则集是用户自己的，他应该能直接改线上那份，而不是在本地越堆越多的覆盖条目。两种情况都要支持，所以分两种模式。

**模式按规则集定，不按整个工具定**：同一份 Clash 配置里，可能同时有别人的规则集（订阅）和自己的规则集（支配）。

| | 订阅 | 支配 |
|---|---|---|
| 判定 | 没有它的写入凭据 | `settings.json` 里为它的来源配了写入凭据，且服务端接受这把凭据 |
| 正本 | 线上，别人的 | 线上，自己的 |
| 本地 | 读取来的副本，只用来判断「已有规则」 | 读取来的副本，只用来显示与判断「已有规则」 |
| 改类 | 在覆盖层写一条（第二节） | 经写入协议，从原规则集删、往目标规则集加，一次完成（第三节） |
| 删除 | 做不到（见第二节） | 经写入协议删掉 |
| 生效 | 覆盖层是 `type: file`，要在 Clash Verge 里重新激活 | 服务端返回已上线后，让内核立即重新取这个规则集 |

## 二、订阅模式：覆盖

- **覆盖层**是 Clash 配置里排在最前的 `type: file` 规则集（现在 README 里叫「收件箱」，每类一个，按 `rules` 里的顺序认）。它是用户自己的规则，**不会被自动清空**。
- 对一条订阅来的条目「改为 直连 / 代理 / 拉黑」，就是在目标类的覆盖层写一条同样的条目。覆盖层排在前面，所以它生效。
- **删除做不到**：覆盖只能表达「归到某一类」，表达不了「当作没列过」。在 `MATCH,REJECT` 兜底的配置下，删掉一条放行规则约等于改为拉黑，界面上就这样提供，并写明两者的差别：改为拉黑后，这个域名不会再进待审。删掉一条拉黑规则，没有对应的覆盖写法。
- **本地副本由 clash-review 自己按网址取**，与内核取的走同一条线路（规则集的 `proxy` 字段，没写就按工具现有的代理回退）。不能依赖分发规则的一方把文件写到 `path` 处：那样 clash-review 就依赖上了某个特定的服务端，也就没有解耦（v1.1.0 就是这样，见第六节）。
- `tidy` 照旧：覆盖层里的条目，如果订阅来的同类规则集已经有了，列为可清理。

## 三、支配模式：直接改线上

- 对一条来自自己规则集的条目改类或删除，经写入协议（第四节）直接改线上，本地不留覆盖条目。
- 审查时新归类的条目，写进这一类的**默认目标规则集**。一类只有一个自己的规则集时就是它；有多个时（比如服务端分了「各平台公用」与「本平台」两层）要在 `settings.json` 里指定，没指定时 `status` 报出来，网页让用户逐条选。分层是服务端的事，clash-review 只看到几个规则集。
- **生效**：写入返回「已上线」后，clash-review 对受影响的规则集调用内核的 `PUT /providers/rules/<名字>` 让它立即重新取，再用 `GET /providers/rules` 的 `ruleCount` 核对条目数。其它设备按各自的更新间隔取到。
- **连不上服务端时明确报错，不自动改写到覆盖层。** 自动回落就需要一个事后把覆盖条目搬上线、再清掉的程序，又回到第六节否定的做法。用户可以手动选择「先在本地覆盖」，这时它就是一条普通的订阅模式覆盖。
- 写入凭据只在 clash-review 的后端（Python 进程）里使用，不进 Clash 配置，不进网址，不发给浏览器。网页发起的写操作沿用现有的防护（自定义请求头、校验 Origin）。

## 四、写入协议（草案 v1）

读取不需要新协议：就是 Clash 的 `type: http` 规则集网址，`format: yaml`（`payload:` 列表）或 `text`。下面只约定写入。

### 来源与凭据

- 一个**来源**是一个服务端，对应一个 `origin`（协议 + 主机 + 端口）。Clash 配置里网址落在这个 origin 下的规则集都属于它。
- `settings.json` 为每个来源写：写入接口的基地址 `endpoint`、凭据文件 `key_file`。凭据文件里只有一行密钥，不放进 `settings.json` 本身。
- 请求带 `Authorization: Bearer <密钥>`。写入密钥与设备读取用的密钥（如果服务端有）必须是不同的两把。

### 接口

| 请求 | 作用 | 返回 |
|---|---|---|
| `GET {endpoint}/rulesets` | 列出这个来源里凭据能写的规则集 | `[{"id", "behavior": "domain" \| "ipcidr", "path", "version", "count"}]`。`path` 是读取网址的结尾部分，clash-review 用「同一 origin 且网址以它结尾」把 Clash 里的规则集对应到 `id`，这样网址里带的设备密钥不必写进设置 |
| `GET {endpoint}/rulesets/{id}` | 读一个规则集 | `{"version", "entries": [...]}` |
| `POST {endpoint}/changes` | 提交一批改动，**整批原子**：要么全部生效，要么都不生效 | 见下 |

`POST /changes` 的请求体：

```json
{
  "base": {"<id>": "<读到的 version>", "...": "..."},
  "ops": [
    {"op": "remove", "ruleset": "<id>", "entry": "+.example.com"},
    {"op": "add",    "ruleset": "<id>", "entry": "+.example.com"}
  ]
}
```

- **改类**就是同一批里的一条 `remove` 加一条 `add`。它必须原子：中途失败只剩一半，这个条目就会凭空消失或同时留在两类里。
- `base` 列出这批涉及的每个规则集读到时的 `version`。任何一个对不上（期间别处改过）→ `409`，返回这些规则集当前的 `version`，不做任何改动。clash-review 重新读取、重新做写入前的检查，再交给用户决定。
- 服务端校验条目：域名写法、`+.` 前缀、CIDR 合法；单个 IP 必须写成 `/32` 或 `/128`（mihomo 会跳过裸 IP，见 README 第六节）。不合法 → `422`，逐条写明原因。
- `add` 的条目已存在、`remove` 的条目不存在：不算错，结果里标为「无变化」。
- 成功时：
  - `200`：新内容**已经**能从读取网址取到。返回 `{"versions": {"<id>": "<新 version>"}, "results": [...]}`；
  - `202`：服务端还要构建、部署，返回 `Location`，clash-review 轮询它直到返回 `200` 再让内核重新取。轮询有上限，超时就报「已提交但尚未上线」，不重复提交。
- 凭据不对 → `401`；凭据对但无权写这个规则集 → `403`。

### 不在协议里的

- 一个规则集属于拉黑、直连还是代理：这由各设备的 Clash 配置里 `RULE-SET` 那一行决定，不是规则集本身的属性。clash-review 从本机的 Clash 配置读。
- 服务端怎样存、怎样构建、分几层、给哪些设备生成什么格式。

## 五、clash-review 要改的

- 规则页左栏列出全部规则集，按来源分组，每个标明订阅还是支配；搜索框搜全部。
- 条目操作按第一节的表格：支配的直接改线上；订阅的写覆盖层，删除按第二节处理。
- `status`：每个来源连得上没有、凭据有没有被接受、每类的默认目标规则集定了没有、内核的条目数与线上是否一致。
- 订阅来的规则集由 clash-review 自己按网址取（第二节），不再读 `path` 处的缓存。

## 六、否定结论

- **收件箱加搬运**（作者本机 2026-09-25 的做法）：clash-review 只写本地收件箱，另一个程序把新条目并入规则集的仓库、推送、部署，等 Clash 取回线上后再清空收件箱。问题：编辑工具看不到、也改不了真正的规则，规则页里只有一个随时被清空的中转站；一条规则要多次复制、跑很多步才生效，任何一步失败都会卡住；改已有规则还得另造一条「删除请求」通道。根源是编辑方没有写线上正本的权限，只能间接写。
- **本机文件为正本、线上只做单向发布**：规则集就不再是「线上的、谁都能订阅的」，clash-review 也得懂某个特定服务端的分层结构，两者又耦合在一起。多台设备本来就需要线上那份。
- **v1.1.0 读 `path` 处的缓存判断「已有规则」**：在 Clash Verge 服务模式下，内核取来的文件写在普通用户读不到的目录，`path` 处的文件内核不再更新，只能靠分发规则的一方另外写一份。这让 clash-review 依赖上了特定的服务端，改为自己按网址取。

## 七、待定

- 支配模式下，覆盖层里如果已经有指向自己规则集条目的覆盖（以前留下的），是否提供「并入线上」的一键操作。
- `202` 的轮询间隔与上限。
- 一个来源的写入接口地址能否由服务端自己声明（比如在读取的响应头里给出），让用户只需配凭据。
